# День 02 — Управление форматом ответа

[← К списку заданий](../README.md) · [Главная страница проекта](../../README.md)

- **Дата:** 1 сентября 2026
- **Статус:** выполнено ✅

## Задание

Отправить один и тот же запрос с разным уровнем контроля:

1. без дополнительных ограничений;
2. с явно заданным форматом ответа;
3. с ограничением длины;
4. с условием завершения ответа.

Сравнить оба результата, полученных через API.

## Результат

Пользователь вводит один запрос и нажимает **«Сравнить ответы»**. iOS- и web-приложения параллельно отправляют на backend два запроса с одинаковым `message`, но разными режимами:

- `unrestricted` — обычный ответ модели;
- `controlled` — JSON, ограничение длины и явная инструкция завершения.

После загрузки сегмент **«Без контроля / С контролем»** переключает уже полученные результаты. Для каждого ответа отображаются модель, количество токенов и `finish_reason`. В контролируемом режиме клиент декодирует JSON в типизированную модель, а интерфейс отдельно показывает собранную карточку с ответом, ингредиентами и шагами. Исходный JSON остаётся снизу с подписью **«P.S. Исходный ответ модели»**, поэтому результат парсинга можно проверить визуально.

Ассистент ограничен темой еды. Это правило действует в обоих режимах: вопросы о рецептах, продуктах и приготовлении обрабатываются, а запросы вне тематики получают вежливый отказ.

## Управление ответом

### Без ограничений

Backend передаёт исходное сообщение модели без дополнительных параметров формата и длины.

### С ограничениями

Backend сохраняет пользовательское сообщение неизменным и добавляет системную инструкцию:

```text
Верни один валидный JSON-объект с полями status, answer,
ingredients и steps.
Для вопроса о еде используй status = ok.
Для запроса вне темы используй status = out_of_scope,
а ingredients и steps верни пустыми.
Сначала спланируй полный короткий ответ. Не обрывай предложения.
Поле answer — не более 20 слов, ingredients — до 8 элементов,
steps — до 4 законченных коротких шагов.
Используй не более 80 слов во всех текстовых значениях.
Если ответ не помещается, сократи формулировки и убери второстепенные детали.
Заверши ответ сразу после закрывающей фигурной скобки.
```

Дополнительно в запрос DeepSeek передаются API-параметры:

```json
{
  "response_format": { "type": "json_object" },
  "max_tokens": 400
}
```

`max_tokens` служит страховочным техническим потолком и оставляет модели достаточно места, чтобы закрыть JSON. Содержательную длину ограничивают инструкция и независимая проверка 80 слов. Явная инструкция завершения выбрана вместо отдельной stop sequence, чтобы модель закрыла JSON-объект и ответ оставался валидным.

## Гарантия контракта на backend

Инструкция модели сама по себе не считается гарантией. После получения контролируемого ответа Go backend независимо разбирает JSON и проверяет:

- присутствуют ровно четыре поля: `status`, `answer`, `ingredients`, `steps`;
- `status` равен только `ok` или `out_of_scope`;
- `answer` не пустой, а `ingredients` и `steps` являются массивами;
- краткое описание содержит не более 20 слов;
- возвращается не более 8 ингредиентов и 4 шагов;
- суммарная длина текстовых значений не превышает 80 слов;
- для `out_of_scope` используется фиксированный отказ, а оба массива остаются пустыми.

Backend также отклоняет результат с `finish_reason: length`: такой ответ считается оборванным, даже если случайно сохранил валидный JSON. Валидный результат нормализуется в единый JSON-вид. Если модель нарушит хотя бы одно правило, backend вернёт контролируемую upstream-ошибку вместо успешного ответа с неправильной структурой.

## API-контракт

Оба режима используют один endpoint:

```http
POST /v1/chat
Authorization: Bearer <access-token>
Content-Type: application/json
```

```json
{
  "message": "Дай простой рецепт греческого салата.",
  "mode": "controlled"
}
```

```json
{
  "answer": "{\"status\":\"ok\",\"answer\":\"...\",\"ingredients\":[\"...\"],\"steps\":[\"...\"]}",
  "model": "deepseek-v4-flash",
  "mode": "controlled",
  "finishReason": "stop",
  "usage": {
    "promptTokens": 68,
    "completionTokens": 74,
    "totalTokens": 142
  }
}
```

Поле `mode` необязательное: если его не передать, backend использует `unrestricted`. Поэтому API первого дня остаётся совместимым.

## Архитектура

```text
ChatScreen
    ↓
ChatViewModel
    ↓
CompareResponsesUseCase
    ├── SendMessageUseCase(.unrestricted)
    └── SendMessageUseCase(.controlled)
            ↓
ChatRepository → ChatAPI → Go backend → DeepSeek
```

Backend принимает только понятный приложению режим. Настройки конкретного LLM-провайдера остаются внутри DeepSeek-клиента и не протекают в iOS-код.

Для `controlled`-режима `DefaultChatRepository` преобразует строку `answer` в `ControlledFoodAnswer`. Domain-модель хранит одновременно структурированное представление для интерфейса и исходный JSON для демонстрации контракта. SwiftUI не разбирает JSON самостоятельно, а только отображает уже подготовленные данные.

Контракт контролируемого ответа сохраняется даже для неподходящего вопроса. Например, на «Как дела?» модель должна вернуть JSON со `status: out_of_scope`, фиксированной фразой «Я отвечаю только на вопросы о еде и приготовлении. Пожалуйста, задайте вопрос по теме.» и пустыми `ingredients`/`steps`. Backend проверяет эти условия, поэтому принимающая программа может разбирать успешный ответ одинаково при любом входе.

Web-версия использует тот же API-контракт. Браузер обращается к same-origin маршруту `/web-api/chat`, а Caddy добавляет служебную авторизацию только внутри VPS. Секрет не попадает в HTML или JavaScript. Публичное демо защищено лимитом запросов на IP и общим дневным пределом.

## Проверка

- один и тот же текст отправляется в обоих режимах;
- свободный запрос не содержит `response_format` и `max_tokens`;
- контролируемый запрос содержит JSON-формат, лимит и инструкцию завершения;
- backend отклоняет отсутствующие/лишние поля, неверный статус, `null` вместо массивов, превышение лимитов и `finish_reason: length`;
- Go unit-тесты проверяют формирование обоих запросов;
- Swift-тест проверяет параллельный запуск двух режимов;
- Swift-тест проверяет декодирование контролируемого JSON;
- iOS-интерфейс показывает оба результата, переключает их сегментом и визуально сопоставляет распарсенную карточку с исходным JSON.
- web-интерфейс повторяет тот же сценарий на desktop и mobile без регистрации.
