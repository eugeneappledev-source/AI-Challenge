## Задание

Решить одну логическую, алгоритмическую или аналитическую задачу через API четырьмя способами:

1. получить прямой ответ без дополнительных инструкций;
2. добавить инструкцию «решай пошагово»;
3. сначала попросить модель составить промпт, затем решить задачу с его помощью;
4. создать группу экспертов и получить решение от каждого.

После этого сравнить ответы и определить наиболее точный способ.

## Результат

В iOS-приложении появился отдельный экран **«День 3»**. Пользователь может:

- написать собственную задачу;
- выбрать один из трёх проверяемых примеров;
- запустить четыре стратегии одним действием;
- наблюдать прогресс каждой стратегии;
- переключаться между готовыми решениями;
- раскрыть промпт, созданный моделью для meta-prompt;
- отдельно прочитать ответы аналитика, инженера и критика;
- получить итоговые оценки и объяснение AI-арбитра.

После запуска задача фиксируется и отправляется во все четыре стратегии без изменения. Это сохраняет единственную экспериментальную переменную — способ инструктирования модели.

## Контрольная задача

Для демонстрации используется задача с проверяемым ответом:

> Между числами 1 2 3 4 5 6 7 8 9 поставь только знаки + или −, не меняя порядок и не объединяя числа, чтобы получить 100. Найди решение или докажи, что оно невозможно.

Корректный вывод — задача невозможна. Сумма `1 + 2 + ... + 9` равна `45`. Изменение знака любого слагаемого меняет сумму на удвоенное число, поэтому результат всегда остаётся нечётным, а `100` — чётное.

Заранее известный и независимо проверяемый ответ позволяет оценивать не красоту текста, а фактическую корректность рассуждения.

## Четыре стратегии

### 1. Прямой ответ

Backend передаёт исходную задачу как пользовательское сообщение без дополнительных инструкций по способу решения.

```text
<исходная задача>
```

### 2. Пошаговое решение

К той же задаче добавляется явная инструкция:

```text
Решай пошагово. Покажи проверяемые шаги,
отдельно проверь соблюдение всех условий
и заверши однозначным ответом.
```

### 3. Промпт от модели

Стратегия действительно состоит из двух последовательных LLM-вызовов:

1. первая модель получает исходную задачу и создаёт улучшенный промпт без решения;
2. полученный промпт передаётся модели во втором запросе;
3. API возвращает и созданный промпт, и итоговое решение.

Приложение показывает сгенерированный промпт в раскрывающемся блоке, поэтому двухэтапный процесс можно проверить визуально.

### 4. Группа экспертов

Один запрос создаёт три независимые роли:

- **аналитик** ищет строгую логику;
- **инженер** предлагает практический алгоритм;
- **критик** ищет ошибки и проверяет ограничения.

Модель возвращает типизированный JSON с отдельным ответом каждого эксперта и общим выводом. Backend проверяет наличие всех трёх ролей и валидность структуры до отправки результата в приложение.

## AI-арбитр

После получения четырёх решений приложение вызывает отдельный endpoint сравнения. Backend заменяет названия методов метками `A`, `B`, `C`, `D`, чтобы снизить влияние названия стратегии на оценку.

Арбитр должен:

1. самостоятельно решить исходную задачу;
2. сформулировать эталонную проверку;
3. сравнить анонимные ответы;
4. оценить правильность, ясность и качество проверки по шкале 0–10;
5. описать ключевые отличия;
6. выбрать победителя и объяснить решение.

Арбитр остаётся языковой моделью, а не формальным доказательным инструментом. Поэтому приложение прямо предупреждает об этом, а демонстрационные задачи имеют ответы, которые можно проверить независимо.

## Количество запросов

Один эксперимент выполняет пять запросов из iOS к собственному backend:

```text
4 × POST /v1/reasoning/run
1 × POST /v1/reasoning/review
```

Внутри backend это шесть обычных LLM-вызовов:

```text
прямой ответ       1
пошаговое решение  1
meta-prompt        2
группа экспертов   1
AI-арбитр          1
```

Если арбитр нарушает JSON-контракт, backend один раз запрашивает исправление структуры. Повреждённый JSON никогда не считается успешным результатом.

## API-контракты

### Запуск стратегии

```http
POST /v1/reasoning/run
Authorization: Bearer <access-token>
Content-Type: application/json
```

```json
{
  "problem": "Условие задачи",
  "method": "meta_prompt"
}
```

Допустимые методы: `direct`, `step_by_step`, `meta_prompt`, `expert_panel`.

```json
{
  "method": "meta_prompt",
  "answer": "Итоговое решение",
  "generatedPrompt": "Промпт, созданный первым запросом",
  "model": "deepseek-v4-flash",
  "finishReason": "stop",
  "usage": {
    "promptTokens": 100,
    "completionTokens": 200,
    "totalTokens": 300
  }
}
```

### Сравнение решений

```http
POST /v1/reasoning/review
Authorization: Bearer <access-token>
Content-Type: application/json
```

Endpoint принимает исходную задачу и ровно по одному результату каждого метода. В ответ возвращаются `winner`, `verdict`, `referenceAnswer`, `differences` и оценки всех стратегий.

## Архитектура iOS

```text
ReasoningComparisonScreen
        ↓
ReasoningComparisonViewModel
        ↓
CompareReasoningStrategiesUseCase
        ↓
ReasoningRepository
        ↓
DefaultReasoningRepository → ReasoningAPI
        ↓
Go backend → DeepSeek
```

Use case параллельно запускает четыре стратегии и сообщает ViewModel о каждом завершённом результате. Когда все ответы готовы, он последовательно запрашивает оценку арбитра.

## Проверка

- Go unit-тесты проверяют все четыре стратегии и двухэтапный meta-prompt;
- отдельный тест проверяет анонимное сопоставление результатов арбитром;
- проверяется восстановление однократно повреждённого JSON;
- transport-тесты проверяют оба новых endpoint;
- Swift-тест подтверждает передачу одной задачи во все четыре метода и последующий review;
- iOS-проект собирается для Simulator;
- выполнен реальный сквозной прогон через DeepSeek.
